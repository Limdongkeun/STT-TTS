# ProjectWatch 앱에 '음성 데이터 모으기' 붙이기 — 전달 문서

> 2026-11-18 · STT-TTS(가족비서 음성) 쪽에서 ProjectWatch 앱 작업 세션으로 넘기는 요구사항이다.
> 구현 방식(화면 구조, DB, 저장소)은 ProjectWatch 레포 관례를 따른다. 이 문서는 **무엇이 필요한지와 넘겨받을 데이터 모양**만 정한다.
> 함께 넘기는 파일: `recording_items.json`(녹음 문제 991개, 버전 2026-11-20).
> 2026-11-20 바뀜: '약한 낱말' 문장 102개(S790~S891, 분류 `약한 낱말`, type `read`)를 끝에 더했다. 앞 번호(S001~S789, P001~P100)는 그대로다. 시험에서 계속 틀린 낱말(하원, 현장학습 동의서, 부르펜 계열, 아내가·아내한테, 콩이, 소윤이, 먹였어 등)이라 **먼저 녹음하도록 앞쪽에 보여 주면 좋다**.

## 1. 왜 하나

- 가족비서 STT(맥 Qwen3-ASR 한국어판)를 **실제 사람 목소리**로 추가 학습하려고 한다. 기계 목소리로 한 학습은 실패했다.
- 팀원이 이미 쓰는 ProjectWatch 앱에서 녹음해 회사 서버에 쌓으면, STT-TTS 쪽은 **쌓인 데이터만 내려받아** 학습한다(학습은 회사 107 GPU).
- 첫 목표: 약 10명 × 150개 = 1,500개(약 1.5시간). 회의 녹음은 쓰지 않는다(2026-11-18 사용자 결정).
- 참여자 동의는 받았다(사용자 확인 2026-11-18). 그래도 앱 안에서 한 번 더 확인받고 기록을 남긴다(§3).

## 2. 녹음 문제 (`recording_items.json`)

```json
{"version": "2026-11-20", "items": [
  {"id": "S001", "type": "read", "category": "일정", "text": "이번 주말에 우리 가족 뭐 하기로 했지?"},
  {"id": "S189", "type": "short", "category": "짧은 말", "text": "응"},
  {"id": "P001", "type": "situation", "category": "일정", "prompt": "이번 주말에 가족끼리 무슨 약속이 있는지 비서에게 물어보세요."}
]}
```

| type | 개수 | 화면에 보여 줄 것 | 정답 글(label) |
|---|---|---|---|
| `read` | 762 | `text`를 그대로 읽게 한다 | `text` 그대로. 다르게 읽었으면 사용자가 고친 글 |
| `short` | 27 | `text`(응, 아니, 잠깐…)를 말하게 한다 | `text` |
| `situation` | 100 | `prompt`(상황)만 보여 주고 **자기 말로** 말하게 한다 | **사용자가 확인·수정한 글**(필수) |

- `id`는 바꾸지 않는다. `S` 번호는 STT-TTS 학습 문장 파일의 줄 순서와 같다(학습 쪽이 이 번호로 짝짓는다).
- 시험표(평가용) 문장은 일부러 빠져 있다. 앱에서 문장을 지어내거나 바꾸지 않는다.
- 문장 목록이 바뀌면 STT-TTS 쪽이 새 JSON(`version` 바뀜)을 넘긴다. 이미 받은 녹음은 그때의 `version`·`id`로 남긴다.

## 3. 사용자 흐름

1. **처음 들어올 때 — 동의 확인**
   - 보여 줄 것: 목적(가족비서 음성 인식 모델 학습·평가), 저장 위치(회사 서버, 외부 클라우드로 보내지 않음), 보관 기간(예: 학습 종료 후 1년, 회사가 정함), 볼 수 있는 사람(학습 담당자), 철회 방법(언제든 내 녹음 전체 삭제).
   - '동의하고 시작' → 동의 시각·동의 문구 버전(`consent_version`)을 저장한다. 동의 전에는 녹음 화면에 들어갈 수 없다.
2. **오늘의 묶음** — 한 번에 10개씩 보여 준다(지루하지 않게). 한 사람 목표는 150개다.
   - 섞는 비율: `read` 60% · `situation` 27% · `short` 13%(150개 기준 90 · 40 · 20).
   - 배정은 **아직 녹음이 적은 문제부터**(전체 사람 기준). 같은 사람에게 같은 문제를 두 번 주지 않는다.
3. **한 문제 녹음**
   - 문제를 보여 준다 → 🎤 누르고 말한다 → 말이 끝나면 저절로 멈추거나(조용함 약 1초) 다시 눌러 멈춘다.
   - 바로 들어 보기 ▶ / 다시 녹음 / 건너뛰기 / 올리기.
   - `read`·`short`: 정답 글 칸에 문제 글이 미리 들어 있다. 다르게 읽었으면 고친다.
   - `situation`: 폰 기본 받아쓰기 결과를 초안으로 채워 보여 주고, 사용자가 **실제로 한 말과 똑같이** 고친 뒤 올린다. 초안을 그대로 올리면 '확인함' 표시를 받는다.
   - 정답 글 쓰는 법(화면에 한 줄 안내): 숫자는 '8만 4천 원', '2시 30분', '12월 3일'처럼 아라비아 숫자 + 단위로 쓴다. 군말(음, 어)은 빼도 된다.
4. **내 녹음** — 내가 올린 목록, 다시 듣기, 하나 지우기, **전부 지우고 동의 철회**.

## 4. 녹음 파일

- 형식: **WAV, 16kHz, 모노, 16비트 PCM**(가장 좋음). 어려우면 m4a(AAC) 44.1kHz도 받는다(학습 쪽에서 바꾼다). 소리를 줄이거나 잡음 제거 같은 가공은 **하지 않는다**(원래 소리가 필요하다).
- 길이: 0.5~20초. 0.5초보다 짧거나 거의 무음이면 '다시 녹음해 주세요'로 막는다.
- 앞뒤 여유: 녹음 시작 뒤 0.3초쯤 지나서 말하라고 안내한다(첫 낱말 잘림 방지 — 가족비서 시험에서 실제로 있었다).
- 이어폰 마이크·폰 마이크 모두 받는다. 어떤 기기였는지 메타데이터에 남긴다.

## 5. 서버에 남길 것 (녹음 1개당)

| 칸 | 예 | 설명 |
|---|---|---|
| `clip_id` | uuid | |
| `item_id` | `S123` / `P045` | §2의 id |
| `item_type` | `read` / `short` / `situation` | |
| `items_version` | `2026-11-20` (받은 JSON 의 version 그대로) | |

| `env` | `quiet` / `noisy` | 선택, 사용자가 고름 |
| `app_version`, `recorded_at`, `uploaded_at` | | |

| `status` | `active` / `deleted` | 지우면 파일도 지우고 이 칸만 남기거나 줄 전체 삭제(회사 정책) |

- 저장 위치는 회사 서버 안. 외부 클라우드 STT·AI로 보내지 않는다.
- 볼 수 있는 사람: 학습 담당자(관리자 권한)만. 다른 팀원은 자기 녹음만 본다.

## 6. STT-TTS 쪽이 가져가는 방법 (내보내기)

다음 중 하나면 된다(구현 쉬운 쪽).

- **A. 내보내기 API(추천)**
  - `GET /stt-collection/export?since=<ISO 시각>` → `manifest.jsonl`(한 줄에 녹음 하나, §5 칸들, `status=active`만) + 파일 받기 주소(만료되는 링크)
  - 인증: 학습 담당자 토큰. 토큰은 STT-TTS 맥 키체인에 둔다(코드·문서에 적지 않음).
- **B. 묶음 파일**
  - 관리자가 버튼으로 `zip`(manifest.jsonl + audio/)을 만들어 내 파일함·자료실에 올린다.

`manifest.jsonl` 한 줄 예:

```json
{"clip_id":"…","item_id":"S123","item_type":"read","items_version":"2026-11-18","transcript":"관리비 고지서 왔어","transcript_source":"script","speaker_code":"SPK07","audio":"audio/SPK07/S123_….wav","duration_ms":2410,"device":"iPhone14,2/iOS 27.0.1","env":"quiet","recorded_at":"2026-11-24T10:12:03+09:00"}
```

- 같은 문제를 같은 사람이 다시 녹음하면 마지막 것만 `active`로 둔다.
- 지운 녹음은 다음 내보내기에서 빠져야 한다(STT-TTS 쪽도 지운다).

## 6-1. 확인 화면·녹음 보완 (2026-11-19 추가)

첫 녹음 20개(SPK01·SPK04)를 STT-TTS 쪽에서 맥 STT로 다시 받아 적어 검사했다. 11개가 걸렸다(아래). 앱에서 이렇게 보완해 주면 좋겠다.

**A. 녹음 앞·뒤가 잘린다 (가장 급함)**
- 20개 중 7개가 첫 소리부터 바로 시작한다(앞 무음 0~20ms). 그중 '나중에'는 '중에', '이번 주 분리수거'는 '주 분리수거'로 들렸다 → 앞 음절이 잘린 것으로 보인다. 뒤 무음이 20~40ms뿐인 것도 있다.
- 보완: ① 마이크가 실제로 녹음을 시작한 뒤에만 '말하세요'를 보여 준다. ② 녹음 시작 전 0.5초쯤을 미리 담아 두거나(프리롤), 시작 뒤 0.3초 기다렸다 말하라고 안내한다. ③ 멈춤을 누른 뒤에도 0.5초 더 녹음하고 끝낸다.
- (가족비서 앱에서도 같은 문제가 있었다: 듣기 준비가 끝나기 전에 말을 시작해 첫 낱말이 빠졌고, '말하세요'를 마이크가 녹음을 시작한 뒤에 띄워서 고쳤다.)

**B. 확인 화면에 '폰이 들은 글'을 함께 보여 준다**
1. 정답 칸 위에 '폰이 들은 글'을 회색으로 보여 주고, 문제 글과 다른 낱말만 표시한다.
2. 안내 문구: "폰이 이렇게 들었어요(폰도 틀릴 수 있어요)". 다르다고 정답 칸을 폰 글로 바꾸라는 뜻이 아니다.
3. 정답 칸은 지금처럼 둔다(읽기는 문제 글, 상황은 폰 받아쓰기). 폰 글로 자동으로 바꾸지 않는다.
4. 차이가 크면(글자 30% 넘게 다름) "다시 들어 보시고, 다르게 읽었으면 고치거나 다시 녹음해 주세요"를 띄운다. 올리는 건 막지 않는다.
5. 상황 문제는 올리기 전에 ▶ 다시 듣기를 눈에 띄게 두고 "들린 말과 낱말 하나하나 같은지 확인해 주세요"를 보여 준다. 첫 녹음의 상황 문제 6개가 모두 고치지 않고 확인만 했고, 그중 P049는 폰이 '했다고'를 '있다고'로 적은 채 올라왔다.
6. manifest에 `phone_stt_raw`(폰 받아쓰기 원문, 고치기 전) 칸을 더한다. 읽기·짧은 말·상황 모두.

**C. 정답 칸 아래 한 줄 안내**
- "실제로 한 말을 맞춤법대로 적어요. 소리 나는 대로 쓰지 않고, 다르게 말했으면 말한 대로 고쳐요. 숫자는 8만 4천 원·2시 30분처럼, 음·어는 빼요."

**첫 녹음 검사 결과(참고)**

| 걸린 이유 | 개수 | 예 |
|---|---|---|
| 앞 잘림 의심 | 7 | S786 '나중에'→'중에', P048 '주 분리수거' |
| 정답과 다름 — 상황 문제 | 4 | P049 '있다고'(실제는 '했다고'), P015 '구몬/구문' |
| 정답과 다름 — 읽기 | 3 | S069 '얼마나 썼어'→'얼마 났었어', S582 '틀어라'→'틀었나' |

(한 녹음에 이유가 둘 이상일 수 있다. 걸린 녹음은 학습에서 빼고, 사람이 들어 보고 되살릴 수 있다.)

## 7. 하지 않을 것

- 녹음을 외부 클라우드 STT·LLM에 보내지 않는다(정답 초안은 폰 기본 받아쓰기만).
- 소리 가공(잡음 제거, 크기 맞추기) 하지 않는다.
- 이름·전화번호 같은 개인 정보를 manifest에 넣지 않는다(`speaker_code`만).
- 문제 글을 앱에서 바꾸지 않는다(바꿀 땐 STT-TTS 쪽이 새 JSON을 준다).

## 8. 다 되면 알려 줄 것

- 내보내기 방법(API 주소·토큰 받는 법, 또는 zip 위치)
- 쌓인 개수(사람 수, 녹음 수, 총 길이)
- 녹음 형식이 WAV 16k가 아니면 실제 형식

STT-TTS 쪽은 받은 manifest로 학습 세트를 만들고(`server/finetune/build_dataset.py`), 실기기 평가 녹음 76개로 전후를 비교한 뒤 107 GPU에서 학습한다.
